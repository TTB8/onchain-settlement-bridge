# @bridge/db

The bridge's PostgreSQL 16 schema (Prisma 6.19.3) and the SQL guards that make the ledger's
guarantees physical. Even if application code has a bug, the database refuses to commit an
unbalanced entry, to rewrite history, to move an operation along an illegal edge, or to let a user
account go negative.

Business rules live in `@bridge/domain`. This package does not repeat them in TypeScript: it
gives the engine a schema, a few thin helpers, and a database that fails closed.

- Schema: `prisma/schema.prisma`
- Tables: `prisma/migrations/20261123000000_init/migration.sql` (generated by `prisma migrate diff`)
- Guards and the `account_balance` view: `prisma/migrations/20261123000001_guards/migration.sql`
  (hand-written; every guard has a comment saying which bug it stops)

## Tables

| Table (Prisma model)                   | What it holds                                                                    | Key constraints                                                                                                                                                               |
| -------------------------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `deployment` (Deployment)              | One token + registry pair on one chain                                           | unique (chain_id, token_address); one active per chain; identity immutable; cannot be deactivated while work is in flight                                                     |
| `app_user` (User)                      | A user and their wallet                                                          | wallet lowercase `0x` + 40 hex, unique                                                                                                                                        |
| `account` (Account)                    | Ledger accounts: one `fiat_clearing`, and per user `available`, `held`, `incoming` | fiat_clearing has no user and is a singleton; every other kind has a user; unique (kind, user_id); identity immutable; never deleted                                          |
| `operation` (Operation)                | A deposit, withdrawal or transfer                                                | ref lowercase 32-byte hex, non-zero, unique per deployment; legal transitions only; identity immutable; version +1 per update; parties match type                             |
| `journal_entry` (JournalEntry)         | One step (reserve / settle / reverse) of one operation                           | unique (operation_id, kind); append-only; balanced at commit; sealed by its creating transaction; kind legal for the operation status                                         |
| `posting` (Posting)                    | One debit or credit line                                                         | amount > 0 and equal to the operation's amount; account belongs to the operation's parties or is fiat_clearing; append-only                                                   |
| `outbox_message` (OutboxMessage)       | A contract call waiting to be sent                                               | exactly one subject (operation or compliance change) with the matching signer; (subject, deployment, ref) is a composite FK; payload immutable                                |
| `signer_state` (SignerState)           | The address of each signer per deployment; locked while allocating a nonce       | PK (deployment_id, signer); address immutable                                                                                                                                 |
| `chain_attempt` (ChainAttempt)         | One signed transaction                                                           | identity (outbox, signer, nonce, hash, raw bytes, fees, contract, ref) immutable; never deleted; contract must be the deployment's token or registry; composite FK to outbox  |
| `compliance_change` (ComplianceChange) | A verify / unverify / freeze / unfreeze request                                  | ref unique per deployment; legal transitions only; identity immutable; never deleted                                                                                          |
| `indexed_block` (IndexedBlock)         | A block the indexer read                                                         | PK (deployment_id, number); hashes lowercase hex                                                                                                                              |
| `indexer_state` (IndexerState)         | How far the indexer has read                                                     | PK deployment_id                                                                                                                                                              |
| `chain_event` (ChainEvent)             | One decoded log                                                                  | unique (deployment_id, block_hash, log_index); FK to its block (deleted with it on reorg); fields must match the kind; `amount` is numeric(78,0) to hold any uint256          |
| `reconciliation_run` (ReconciliationRun) | One reconciliation pass                                                        | mismatches is a JSON array, summary a JSON object                                                                                                                             |
| `audit_log` (AuditLog)                 | Every state change                                                               | bigserial id; append-only                                                                                                                                                     |
| `account_balance` (view)               | Derived balance per account                                                      | credit-normal for user accounts (credits - debits), debit-normal for fiat_clearing; read with `readBalances`                                                                   |

Every table that belongs to a deployment carries `deployment_id`, and a trigger refuses changing
it on every one of them.

What guard 5 does **not** enforce: which accounts and sides each step uses (the posting table in
`@bridge/domain` `ledger.ts`). A wrong but balanced pair inside the operation's own accounts
(for example a deposit reserve credited to `available` instead of `incoming`) passes; the test
"DOCUMENTED LIMIT" pins this. Balancing, the overdraft guard and reconciliation are the backstop.

What no guard can stop: the table owner or a superuser can disable triggers. In production the
application must connect as a role that does not own the tables.

## The engine's obligation

The overdraft guard makes a double spend impossible to COMMIT, but a refused commit is a failed
request. To refuse cleanly and early, the engine must read the balance it checks and write the
reservation **in one transaction, under the lock**:

```ts
await prisma.$transaction(async (tx) => {
  // 1. Lock every account the entry will debit or credit, by id, in a stable order.
  await lockRows(tx, 'account', [user.availableId, user.heldId]);
  // 2. Read the derived balance under that lock.
  const [available] = await readBalances(tx, { accountIds: [user.availableId] });
  // 3. Decide with @bridge/domain (assertCanReserve), then insert the operation, the entry and
  //    its postings, and move the operation to ledger_reserved, all in this transaction.
});
```

Rules that follow from the guards:

- `lockRows` sorts ids and locks in ascending order; always lock through it (never in ad hoc
  order) so two transactions cannot deadlock. It throws outside a transaction and when a row is
  missing.
- Write an entry and all its postings in the same transaction (they are sealed at commit), and
  change the operation status in that same transaction (`ledger_reserved` with `reserve`,
  `confirmed` with `settle`, `reversed` with `reverse`); otherwise the commit is refused.
- Every operation UPDATE must set `version` to the version it read plus one, as a literal value
  computed from its read (`SET version = $readVersion + 1`), not `version = version + 1`: the
  literal form is what lets the database refuse a writer working from a stale read.
- Hold `lockSignerState` while allocating a nonce and inserting the attempt.
- Amounts are bigint; JSON columns carry them as decimal strings (`bigintsToDecimal`,
  `bigintFromDecimal`).

## Running

```bash
docker compose up -d postgres                 # DEV Postgres on localhost:5434 (user/password bridge)
pnpm --filter @bridge/db db:generate          # generate the Prisma client (also runs on install)
pnpm --filter @bridge/db test                 # all tests
pnpm --filter @bridge/db test:cov             # with coverage thresholds
DATABASE_URL=... pnpm --filter @bridge/db db:migrate:deploy   # apply migrations (non-destructive)
DATABASE_URL=... pnpm --filter @bridge/db db:seed             # create fiat_clearing (idempotent)
```

Each test file creates a fresh database `bridge_db_test_<random>`, applies the migrations with
`prisma migrate deploy`, and drops it afterwards (also on failure). It connects to the `postgres`
database only to create and drop it, and never touches `bridge` or `bridge_test`. Override the
admin URL with `DB_TEST_ADMIN_URL` (see `.env.example`; DEV credentials only).

To change the schema: edit `schema.prisma`, write a new migration (`prisma migrate diff
--from-migrations ... --to-schema-datamodel ... --script` against a throwaway shadow database),
and never edit an applied migration.
